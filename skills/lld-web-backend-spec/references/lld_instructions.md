# הנחיות אפיון LLD לפיצ'ר Web (צד לקוח, צד שרת ו-CMS)

מסמך זה מבוסס על הפרומפט המקורי של הצוות לאפיון רכיב Web מתוך Figma, ומורחב לפיצ'רים שכוללים צד שרת ותוכן מנוהל. הוא מגדיר את הכללים המדויקים לתוכן של כל טבלה – לא רק השראה כללית. המבנה עצמו, המספור והמזהים מוגדרים ב-`lld_template.md`.

---

## הנחיות כלליות

- הפיצ'ר מופיע בעיצוב בגרסת דסקטופ ובגרסת מובייל, ויש לכסות את שתיהן.
- יש לסווג כל ערך מוצג: מוזן ע"י עורך תוכן, קבוע (מילון, ערך קשיח, נכס סטטי), מגיע מ-API, או נגזר מחישוב.
- יש לתאר את התצוגה ואת הלוגיקה של כל רכיב, כולל נקודות כשל אפשריות: תוכן חסר או משובש, ותוכן שאורכו אינו תואם לעיצוב.
- כל הערה נכתבת בשורה של הרכיב, השדה, הכלל או התרחיש שהיא שייכת לו, ולא בנספח בסוף המסמך – כדי שהמפתח וה-QA ידעו בדיוק למה היא מתייחסת.
- נושאים פתוחים והנחות מרוכזים פעם אחת בסוף הסעיף שהם שייכים לו, עם מזהה. בכל שורה שהם משפיעים עליה מופיעה הפניה למזהה, בלי לשכפל את התיאור.
- אין לפרט התנהגות סטנדרטית שסביבת הפיתוח כבר מטפלת בה. מפרטים רק דרישות ייחודיות לפיצ'ר, חריגות, והתנהגות שדורשת אפיון מפורש.

## סעיף 4 – צד הגולש

### טבלת רכיבים (4.4)

פתיח: משפט תמציתי שמתאר מה מוצג בפיצ'ר, והערות כלליות למפתח ברמת הפיצ'ר כולו. הערה שחלה על כל השורות (למשל "שמות שדות ה-API מסומנים 'צריך לוודא' עד לקבלת החוזה") נכתבת כאן פעם אחת.

כל שורה מייצגת חלק בתצוגה: כותרת, רשימת פריטים, תמונה, תאריך, כפתור וכו'.

1. **ID** – `UI-xx`.
2. **רכיב** – שם קצר.
3. **תיאור ופרטים** – מה מוצג, כולל אייקונים ומיקום כשהם חלק מההגדרה.
4. **מקור התוכן** – אחד או יותר מהבאים, במפורש:
   - שדה CMS: `CMS-xx` ושמו.
   - API: `API-xx` (או פעולה בחוזה קיים) ונתיב השדה, למשל `items[].name`.
   - מילון: מפתח המילון.
   - קבוע.
   - נגזר: הפניה ל-`BR-xx`.
   ברכיב שמשלב כמה מקורות, יש לציין את המקור של כל ערך בנפרד.
5. **לוגיקה ומצבים** – כיצד הרכיב מוצג במצבים שונים, כולל מקרי קצה: תוכן ריק, ארוך מדי, לא תקין.
6. **המחשה** – צילום המסך או קישור ה-Figma של הרכיב.

אין עמודות לרספונסיביות ולנגישות – הן מרוכזות בסעיף 4.5. אין עמודת "אייקון כן/לא" – דרישות אייקון נכתבות בתיאור הרכיב.

**כלל חשוב – רכיבים שתלויים ב-API:** אין להסתפק בתיאור מה מוצג. יש לפרט:
- מתי הקריאה מתבצעת: בטעינת הרכיב, בפעולת משתמש, ברענון תקופתי וכו'.
- מה מפעיל קריאה מחדש.
- איך תגובות שונות משנות את התצוגה: הצלחה, ריק, שגיאה וכשל חלקי.

אם התוכן דורש עיבוד או מיפוי לפני הצגה (המרת קוד לתווית, resolve מ-lookup table, פורמט, חישוב), יש לתאר זאת בעמודת הלוגיקה ולא להניח שערך ה-API זהה לערך המוצג. אם הלוגיקה אינה ידועה, יש לסמן "צריך לוודא" ולהפנות לנושא הפתוח.

**רשימות עם דפדוף, גלילה אופקית או קרוסלה:** יש לציין זאת במפורש, כדי לאפיין את ההתנהגות הרספונסיבית ואת הנגישות של מנגנון הדפדוף, ולא רק את התוכן.

**תאריך או שעה:** יש לתאר את הלוגיקה להמרה לפורמט קריא, עם דוגמאות בשפת המסמך (למשל "לפני 3 שעות", "אתמול").

### רספונסיביות ונגישות (4.5)

- **רספונסיביות:** רק כשיש התנהגות מיוחדת במעבר בין גדלי מסך, או במעבר מאופקי לאנכי.
- **נגישות (רמת AA):** רק התנהגויות שלא באות לידי ביטוי בעיצוב ולא נאכפות אוטומטית ע"י סביבת הפיתוח. למשל: התאמת תגיות H לכותרות, התנהגות רכיב במצב disabled, דילוג ישר לתוכן המרכזי, הקראה של עדכון דינמי, מצב פתוח/סגור של קולפס. אין להתייחס לניגודיות צבעים, גודל טקסט או מיקום ויזואלי אם הם כבר מיושמים בעיצוב.
- כל דרישה מפנה ל-`UI-xx` שהיא חלה עליהם.

### קריטריונים לקבלה (4.6)

קריטריונים שניתן לבדוק, עם הפניה לרכיבים ולתרחישים. לא רק "כל הרכיבים מתנהגים כמתואר", אלא גם המצבים החשובים: מקרי ריק, שגיאה, כשל חלקי, כניסה מ-URL וכו'.

## סעיף 5 – אינטגרציה וכללים עסקיים

### כללים עסקיים (5.1)

כשסעיף 5 לא רלוונטי (אין API ואין תרחיש חוצה מערכות), כללי תצוגה נגזרים – למשל "אין קישור, אין כפתור" או "החלפה כל 6 שניות" – נכתבים בעמודת הלוגיקה של הרכיב ב-4.4, בלי `BR-xx`.

כלל עסקי מנוסח כחוק מפורש ולא כפסקת פרוזה: מה הקלט, מה התנאי ומה התוצאה. לכל כלל יש לציין איזו מערכת מבצעת אותו (Web / Backend / CMS / שירות חיצוני). אם האנליסט בחר "ייקבע ע"י צוות הפיתוח", הכלל עצמו מאופיין במלואו ומיקום הביצוע מפנה ל-`TQ` שהבעלים שלו הוא צוות הפיתוח. כשהמערכת המבצעת זהה לכל הכללים, כותבים אותה פעם אחת מעל הטבלה.

### תרחישים חוצי מערכות (5.2)

לכל תרחיש שעובר בין צד הלקוח, צד השרת וה-CMS יש לפרט:
- מה מפעיל אותו;
- מאיפה מגיעים הנתונים;
- איזו מערכת מבצעת כל כלל;
- מה עובר בין המערכות (קלט ופלט);
- מה הגולש רואה בטעינה, בהצלחה, בתוצאה ריקה, בשגיאה ובכשל חלקי.

דוגמה: אם הגדרות ב-CMS קובעות איך מסננים וממיינים תוצאות משירות חיצוני, יש לציין איפה מתבצעות השליפה, הסינון והמיון, ומה כל מערכת מקבלת ומחזירה.

### חוזי API (5.3)

- **חוזה קיים:** מקבל `API-xx` עם הסימון "(קיים)", קישור לחוזה ורשימת השדות שהפיצ'ר צורך – בלי לשכפל את החוזה. כך גם הפניות לפעולה קיימת נבדקות בבדיקת העקיבות.
- **חוזה חדש או משתנה:** method ו-path, הרשאה, מבנה Request, מבנה Response בהצלחה, ולידציה, וטבלת שגיאות. טבלת השגיאות מכסה לפחות כשל ולידציה (כשיש קלט), ולפי הצורך גם not-found ו-permission-denied, ולכל שגיאה מציינת מה הגולש רואה.
- **מקורות – חוזה קיים:** פרטי החוזה נלקחים רק ממקור מאומת – Swagger/OpenAPI, IDD, אפיון Backend או קוד. פרט חסר מסומן "צריך לוודא" ונרשם כנושא טכני פתוח. אין להציע או להמציא ערכים לחוזה קיים.
- **מקורות – חוזה חדש או משתנה:** אין עדיין מקור מאומת, כי החוזה מוגדר במסמך הזה. לכן מציעים נתיב, שמות שדות, סוגים, קודי סטטוס וערכי `errorCode` לפי המוסכמות של הריפו (או לפי מה שהאנליסט מסר).
  - מסמנים **"(מוצע)" ליד כל ערך מוצע** – לא רק פעם אחת בראש הסעיף, כדי שאיש לא יתייחס להצעה כסופית. הסימון נכתב מחוץ ל-code span (`` `VALUE` (מוצע) ``), כדי שלא ישבור את כיוון הטקסט.
  - בבלוק JSON אי אפשר לסמן כל ערך בלי לשבור את ה-JSON. לכן מסמנים את הבלוק כולו בתווית שלו (`**Request (מוצע):**`), וכל השמות שבו נחשבים מוצעים.
  - ערך שנקבע ישירות ממוסכמה מתועדת של הריפו (למשל "409 לקונפליקט מצב") אינו מסומן "(מוצע)" – המוסכמה היא המקור שלו. מסמנים רק ערכים שנבחרו בשיקול דעת.
  - אותו כלל חל על ישויות ושדות חדשים בסעיף 5.4.
  - נושא טכני פתוח אחד, שהבעלים שלו הוא צוות ה-Backend, מכסה את אישור כל הערכים המוצעים בסעיף.
  - כשאין מוסכמות ידועות שאפשר לבסס עליהן הצעה, מסמנים "צריך לוודא".
  - כללים עסקיים לא מוצעים כך – הם מגיעים מהאנליסט.
- **מוסכמות:** מעדיפים את המוסכמות הקיימות בקוד (שמות, מבנה שגיאה, דפוס הרשאות) על פני מוסכמות חדשות.

### שינויי נתונים ואינטגרציות (5.4–5.5)

- **שינויי נתונים:** ישויות ושדות חדשים או משתנים, אילוצים, והשלכות מיגרציה על נתונים קיימים.
- **אינטגרציות:** לכל שירות חיצוני – מה קורה כשהוא לא זמין, וכיצד זה משפיע על התצוגה.
- **תרשים:** אם זרימה עוברת ביותר משירות אחד או כוללת שלב אסינכרוני, שואלים שאלת כן/לא אחת לפני שמייצרים משהו: "ליצור תרשים רצף דרך מחבר draw.io?". לעולם לא מייצרים בלי לשאול. אם התשובה שלילית, לא ברורה ("לא ידוע"), או שאין מחבר מתאים, מתארים את הזרימה במילים, בלי לרשום הנחה.

## סעיף 6 – צד העורך

### מבנה התוכן ושדות (6.4)

פתיח: משפט תמציתי שמתאר מה עורך התוכן מזין כשהוא משלב את הרכיב בדף או יוצר את הדף.

המטרה היא שגם המפתח וגם עורך התוכן יבינו את המבנה ואת חוויית העריכה, ולא רק את מבנה הנתונים.

**ארגון הטבלאות לפי שיקול האנליסט:**
- טבלאות נפרדות כשהן מבהירות, בעיקר למבנים מורכבים או חוזרים (Block List, רשימות פריטים).
- טבלה מאוחדת עם שורות קבוצה (`| | **רמה 2 – ...** |`) כשהיא מציגה את ההיררכיה בצורה ברורה יותר.

**עמודות:** ID (`CMS-xx`), שם שדה, תיאור (תפקיד השדה), סוג שדה, חובה, בקרות ומגבלות, הערות לעורך.
- ברירת מחדל נכתבת בעמודת הבקרות כשהיא רלוונטית, בלי עמודה ייעודית.
- מידע על אינדוקס בחיפוש נוסף רק כשהפיצ'ר כולל חיפוש באתר שרלוונטי לשדה.

**שינויי סכמה בסוג תוכן קיים** (למשל הוספת שדה לסוג תוכן שכבר קיים באתר) נכתבים כאן בלבד, בטבלת סוג התוכן, עם הערה "שדה חדש בסוג תוכן קיים". הם לא נכתבים בסעיף 5.4.

**בחלק זה אין לציין לוגיקה של אופן הצגת השדה באתר** – זו שייכת לטבלת הרכיבים בסעיף 4.4.

**כלל חשוב – תוכן שמגיע מ-API או ערכים קבועים:** אין ליצור עבורם שדות CMS. בפתיח של התבנית מציינים במפורש אילו ערכים מגיעים מ-API או קבועים, ואת כל האלמנטים המוצגים מהם מאפיינים בסעיף 4.4.

### סוגי שדות ב-Umbraco 13

כשה-CMS הוא Umbraco 13, יש להשתמש תמיד בשם המדויק של עורך המאפיין (property editor), ולא בתווית כללית כמו "טקסט" או "Textbox". כך המפתחים יכולים להגדיר את ה-CMS בדיוק לפי האפיון. עורכים מובנים נפוצים:

| צורך | עורך ב-Umbraco 13 |
|---|---|
| טקסט בשורה אחת | Textstring |
| טקסט רב-שורתי ללא עיצוב | Textarea |
| טקסט מעוצב (בולטים, קישורים, הדגשות) | Rich Text Editor |
| Markdown | Markdown Editor |
| מספר שלם / עשרוני | Numeric / Decimal |
| טווח מספרי בגרירה | Slider |
| כן/לא | Toggle |
| אימייל | Email Address |
| תאריך / תאריך ושעה | Date Picker / Date Picker with time |
| בחירה מרשימה קבועה | Dropdown (יחידה או מרובה), Radiobox, Checkbox List |
| רשימת מחרוזות חוזרת | Repeatable Textstrings |
| תגיות | Tags |
| צבע מרשימה מוגדרת / צבע חופשי | Color Picker / Eye Dropper Color Picker |
| בחירת פריט תוכן אחד | Content Picker |
| בחירת כמה פריטים מהעץ | Multinode Treepicker |
| תמונה או מדיה | Media Picker |
| טקסט חלופי (alt) לתמונה | Textstring נפרד ליד ה-Media Picker, או מאפיין של פריט המדיה בספריית המדיה – לפי מוסכמת הפרויקט (לאשר) |
| חיתוך תמונה | Image Cropper |
| העלאת קובץ | File Upload |
| קישורים (פנימיים או חיצוניים) | Multi URL Picker |
| חבר / משתמש | Member Picker / User Picker |
| רשימת בלוקים חוזרים | Block List |
| פריסת בלוקים בגריד | Block Grid |
| ערך לקריאה בלבד | Label |

- יש לציין את ההגדרות הרלוונטיות של העורך בעמודת הבקרות (למשל Media Picker – תמונה אחת; Multinode Treepicker – עד 2 פריטים; Content Picker – רק סוג תוכן X).
- עורך מותאם אישית או מתוסף קהילתי נכתב בשם שלו בפרויקט, עם הערה שהוא אינו מובנה. אם לא ברור שהוא קיים בפרויקט, נרשם נושא טכני פתוח.
- אם ה-CMS אינו Umbraco 13, משתמשים בשמות העורכים המדויקים של אותו CMS ואותה גרסה, לפי אישור האנליסט או הקוד.

### אופן הגעת התוכן לאתר (6.5)

לכל שדה או קבוצת שדות יש לפרט:
- איפה הוא נצרך (`UI-xx` / `SC-xx` / `API-xx`);
- איזה עיבוד או מיפוי עובר עליו;
- מה קורה כשהוא חסר.

כמו כן יש לפרט caching ועדכניות: תוך כמה זמן שינוי שפורסם מופיע באתר. אם זה ייקבע ע"י צוות הפיתוח, מפנים ל-TQ.

### הרשאות ו-Work Flow (6.6–6.7)

- **הרשאות:** מי יכול ליצור, לערוך, לאשר ולפרסם.
- **Work Flow:** כשקיים תהליך מוכר, מפנים אליו. אם האנליסט ציין שהפירוט לא חשוב בפיצ'ר הזה, ההפניה מספיקה.

## כלל סיכום

לפני הצגת המסמך:
- כל מזהה שמופיע מוגדר, ולכל הגדרה יש הפניה (`scripts/trace_check.py`).
- כל מסך, רכיב, פעולת API וכלל תוכן מהמקורות מכוסה במסמך או מסומן במפורש כמחוץ להיקף.
